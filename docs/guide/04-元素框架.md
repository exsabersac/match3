# 04 元素框架

> 本章讲规则层怎么做到「新元素只写 instance 加一个条目，主流程不用改」，以及加一个元素实际要碰哪些文件。
> 能力表、规则顺序表、扩展钩子的完整清单在 [architecture.md「元素框架与事件」](../architecture.md#元素框架与事件)；
> 元素类的写法演变见 [haskell-features/02-类型类与抽象.md](../haskell-features/02-类型类与抽象.md) 与 [09-规则去重.md](../haskell-features/09-规则去重.md)。

## 1. 设计思路

框架模仿 xmonad 的 `LayoutClass` / `LayoutModifier` / `Message`（对照表见 [architecture.md「与 xmonad LayoutClass 的对照」](../architecture.md#与-xmonad-layoutclass-的对照)）：

- **每种东西一个类型、一个 instance**，状态放在值里（例如 `newtype Fuzzball = Fuzzball Int`）。
- **主流程只问注册表**：「这一格能不能交换？被炸到怎么反应？会不会下落？步末做什么？」，不点名任何具体元素。
- **能力是数据**：元素类只有 `name` / `toCell` / `caps` 三个方法，`caps` 返回一份能力记录 `Caps`（第 9 刀 `ac211d8`）。
  元素声明自己有哪些能力，没声明的取原型的缺省。

演变：第二刀 2b（`51b1cfa`）先做了扁平记录 `ElementDef` + 注册表；元素类原型 `9ae6a7b` → 迁移 `b30cecd`（删掉 `ElementDef`）→ 按功能分文件 `2121bf8`；
段 4（`7630d8b`）把主流程里残留的专门分支（彩虹取色、彩蛋、飞碟、皮带、传送门、地毯……）收进框架；第 9 刀拆成能力记录；
可扩展性 P2（`b5deb86`）再加显示能力 `ViewCaps`。

## 2. 三类元素

| 类别 | 类型类 | 存在包装 | 在哪里 | 内置实例 |
|------|--------|----------|--------|----------|
| 本体（格子里的东西） | `Element`（`src/Match3/Element/Class.hs:243`） | `SomeElement`（`:363`） | 格子本身 | 24 个（`src/Match3/Element/Builtin/{Gem,Obstacle,Collectible,Actor,Ground}.hs`） |
| 修饰器（冰、叠层） | `Modifier`（`Class.hs:410`） | `SomeModifier`（`:436`） | 宝石格的冰层 / 叠层字段 | 9 个（`Builtin/Layer.hs`：冰 + 草、藤、巧克力、迷雾、锁链、冰冻、窗帘、蒸汽） |
| 关卡级元素（不在格子里的机制） | `LevelElement`（`Class.hs:524`） | `SomeLevelElement`（`:538`） | `GameState.gsLevelElems` | 8 个（`Builtin/Level.hs`：飞碟、皮带、传送门、地毯、地面层、L/T 炸弹开关、魔力鸟组合开关、饼干掉落口） |

地面层元素（果冻 `Jelly`、魔法地格 `MagicGround`，`Builtin/Ground.hs`）是 `Element` 实例，但经 `groundEntry` 注册、层数存在关卡级的地面层 `GroundLayer` 里，不占格。

### 2.1 本体：`Element`

```haskell
class (Show e, Eq e, Typeable e) => Element e where
  name   :: e -> ElementName
  toCell :: e -> Cell
  default toCell :: Coercible e Int => e -> Cell      -- Int newtype 元素不用写
  toCell e = Custom (name e) (CustomState (coerce e))
  caps   :: e -> Caps
  caps _ = capsOf Piece
```

一个完整的内置元素（`src/Match3/Element/Builtin/Actor.hs:94-100`）：

```haskell
newtype Fuzzball = Fuzzball Int
  deriving (Eq, Show)

instance Element Fuzzball where
  name _ = "fuzzball"
  caps _ = blocker [breaks, onAdjacent 190 fuzzballAdjacent, counts (CountNamed "fuzzball"), atEnd (moveRule 20 fuzzballRun), labelled "毛球"]
```

读法：原型 `blocker`（挡交换、不点火、会下落、洗牌保留），能力：被命中即碎（`breaks`）、邻格消除时的反应（顺序号 190）、
按名字计数、步末在 `PhaseMove` 阶段第 20 位跳格、目标中文名「毛球」。能力简写都在 `src/Match3/Element/Caps.hs`
（原型 `piece` / `blocker` / `fixed` 在 `:141-149`，显示能力 `displays` / `labelled` / `loseHintIs` 在 `:285-293`）。
`Cap` 是 `Dual (Endo Caps)` 的 newtype，能力列表按书写顺序叠加（Haskell 特性第 9 项）。

### 2.2 修饰器：`Modifier`

修饰器只覆盖要改的方法（`Class.hs:410-432`）：`modApply`（写回格子）、`modBlocksMatch` / `modBlocksSwap`、`modActivates`、
`modOnHit`（命中时 `Pierce` 不管 / `Keep m'` 换层 / `Remove` 揭掉 / `Shatter` 连本格一起碎，`:402`）、`modStripOnClear`、`modAdjacent`、`modEnd`。

冰层（`Builtin/Layer.hs:52`）：

```haskell
instance Modifier Ice where
  modName _ = "ice"
  modActivates (Ice n) = Just (n <= 1)
  modOnHit (Ice n)
    | n > 1 = Keep (Ice (n - 1))      -- 多层冰只削一层
    | otherwise = Shatter             -- 末层冰随宝石一起碎
```

一个格子的完整元素值由注册表拼出来（`src/Match3/Element/Registry.hs:344`）：

```haskell
elementOf reg cell = foldr (\(SomeModifier m) e -> modify m e) (bodyOf reg cell) (upperOf reg cell)
```

即「冰 → 叠层 → 本体」自上而下包起来，`Modified`（`Class.hs` 中 `instance Element Modified`）定义了组合规则：
挡匹配 / 挡交换任一层即挡；点火与命中自上而下第一个有意见的层决定；名字、颜色、计数取最里面的本体；规则类能力只在本体原型上取。

### 2.3 关卡级元素与消息

```haskell
class (Typeable l, Eq l, Show l) => LevelElement l where      -- Class.hs:524
  levelName  :: l -> ElementName
  levelReply :: l -> SomeMessage -> Maybe (SomeMessage, l)    -- 回复 + 推进后的自己
  levelStart :: Level -> l -> l                               -- 从关卡记录取开局状态
  levelCore  :: l -> Bool                                     -- 核心元素（地面层）不用注册
```

消息是开放的（`src/Match3/Element/Message.hs`）：任何 `Typeable` 类型写一个空 instance 就能当消息，收方用 `fromMessage` 按类型认领。
主流程在流水线的固定节拍上用 `askLevelsIn`（`src/Match3/Element/Level.hs:80`）发问：问题和回复同类型，按注册顺序**折叠所有回复者**（前一个的回复是后一个的问题），各自推进后的状态写回 `gsLevelElems`。

| 消息 | 节拍（谁发） | 内置回复者 |
|------|-------------|-----------|
| `Shaping` | 每步结算开始，换特殊块形状表（`levelRegistryIn`） | L/T 炸弹开关 `BombShapes`（第 41 关） |
| `Morphing` | 交换成立前（`morphIn`） | 魔力鸟组合开关 `RainbowCombos`（第 44 关） |
| `Settling` | 每次沉降之后（钩子 `onSettle`） | 传送门 `PortalLevel` |
| `Refilling` | 补子前，换补子策略（钩子 `hookRefill`） | 掉落口 `CookieDrop`（第 46、47 关） |
| `Refilled` | 补子之后的整轮吸收（钩子 `onAbsorb`） | 飞碟 `UfoLevel` |
| `EndTicked` / `AvoidCells` | 步末 `belt` / `move` 阶段 | 皮带 `BeltLevel` |
| `WallCells` | 步末 `move` 阶段 | 传送门 `PortalLevel` |
| `GroundHit` | 结算汇总（`hitGroundIn`） | 地面层 `GroundLayer` |
| `Covering` | 结算汇总（`coverIn`） | 地毯 `CarpetLevel` |
| `Judging` | 胜负判定后（`judgeIn`） | 无（扩展用；内置结局不变，测试 `judge_default_no_replier`） |

钩子记录 `LevelHooks`（`src/Match3/Board/Hooks.hs:20`）是 `Board` 层看到的唯一接口（第 7a 刀）：Board 层只调钩子，不知道背后是哪种关卡级元素。

**格子元素的步末行为不走消息**，而是注册表里排好序的步末规则 `EndRule`（`src/Match3/Element/Types.hs:114`：阶段、顺序号、执行函数、引爆种子、步末空洞），见 [03 §2.5](03-一步棋的生命周期.md#25-步末阶段)。
元素类里虽然有 `stMessage` / `sendMessage`，主流程目前不给格子元素发消息（只有 `test/Spec/ElementClass.hs` 演示）。

## 3. 注册表

`src/Match3/Element/Registry.hs`。一个条目 = 名字 + 槽位 + 原型 + 放置函数：

| 构造函数 | 用途 |
|----------|------|
| `bodyEntry` | 内置构造器的本体（`Stone` / `Chest` …），槽位由原型写回的格子推出 |
| `customEntry` / `customEntryWith` | `Custom 名字 状态` 本体（新元素都用它） |
| `modifierEntry` | 冰 / 叠层 |
| `groundEntry` | 地面层元素 |
| `inertEntry` | 惰性占格（挡交换、不点火、会下落、打不动） |

建表时把条目的规则按顺序号排好存进 `Registry`（`:171`）：邻格规则 `regAdjacent`（按 `arOrder`）、步末规则 `regEnd`（按阶段和 `erOrder`）、
成对交换规则 `regSwap`、开启规则、形状表 `regShapes`、组合表 `regCombos`、补子策略 `regRefill`、关卡级元素 `regLevel`。
主流程的规则查询都是 `…With :: Registry -> …`（`Registry.hs` 里有 38 个），例如 `swapBlockedWith`（`:379`）、`swapOpeningWith`（`:564`）。
显示查询 `faceFieldsWith` / `displayLabelWith` / `loseHintWith` 读 `ViewCaps`。

内置注册表 `defaultRegistry`（`src/Match3/Element/Builtin.hs:90`）= `mkRegistry builtinDefs` 再注册 7 个关卡级元素、换上内置形状表与组合表。条目在 `builtinDefs`（`:97`，36 条）里**只在末尾追加、不重排**：源码注释写明注册顺序就是元素查询快照 `R` 行锁定的顺序。
测试 / 扩展元素用 `register` / `registerLevel` 加进一份新注册表，再走 `…With` 入口或 `match3GameWith reg`。

## 4. 新增一个元素：完整触点清单

依据：[architecture.md「新增一种元素的步骤」](../architecture.md#新增一种元素的步骤)、[web.md §2.3「新元素什么时候要改 cells.js」](../web.md#23-js-渲染器)、
近期元素提交的实际改动（例如变色龙 `c89f452` 改了 36 个文件，网页跟进 `add73de` 又改 12 个），以及可扩展性 P1 / P2 之后省掉的步骤。
可扩展性审核（仓库外的 `/workspace/match3-extensibility-report.md`，`4c59620` 时）实测：最近 5 个新元素平均每个碰 30–39 个文件，大头在前端、测试数字和文档；
P1（`9c9c0b9`）把测试里写死的数量集中到 `Inventory`，P2（`b5deb86` / `32b772b`）去掉了 `View` / 网页 `Api` / `GoalLabel` / JS 颜色表里的按名特判。

## 5. 框架的边界（还做不到的）

摘自 [architecture.md「专门分支的收编」的「遗留」](../architecture.md#专门分支的收编段-4) 与可扩展性审核：

- 需要**新节拍**的关卡级元素（节拍由主流程在固定位置发出）仍要改主流程。
- `Custom` 只能存一个 `Int`；`boardSeed = fnv . show` 把 `Show Cell` 的文本钉成了行为的一部分（毛球 / 雪怪按盘面散列选格），所以 `Cell` 的表示实际上改不动。
- 内置元素的早期构造器（`Stone` … `Countdown`）仍在 `CellContents` 里，没有统一成 `Custom`。
- 前端每个有专门画法的元素要写三份（桌面贴图、桌面几何、网页 JS）；审计第 12 项（合并 `*Prim` / `*Art`）按建议没做（`docs/backlog.md` §4）。
