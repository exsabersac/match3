## 0. 一句话

在已有代码里找四处**本来就在手写类型类机制**的地方，换成语言自带的抽象：
newtype 的「和底层一样」的实例改成**派生**；六个元素重复写的 `toCell` 收成一个**带约束的缺省方法**；

## 1. 这四个特性是什么

### 1.1 DerivingStrategies / GND

`newtype ElementName = ElementName String` 想要和 `String` **一模一样**的 `Show`，有三种来源：

| 策略 | 写法 | 得到的 `show (ElementName "x")` |
|------|------|------|
| stock（标准派生） | `deriving stock Show` | `ElementName {unElementName = "x"}`（带构造器名） |
| newtype（GND） | `deriving newtype Show` | `"x"`：直接拿 `String` 的实例字典来用 |
| via | `deriving Show via String` | `"x"`：拿「表示相同的另一个类型」的实例来用（newtype 策略是它的特例） |

`GeneralizedNewtypeDeriving`（GND）的原理是 `Data.Coerce.coerce`：newtype 和底层类型运行时表示相同，
所以 `String` 的 `showsPrec :: Int -> String -> ShowS` 可以零开销地当成 `Int -> ElementName -> ShowS` 用。
`DerivingStrategies` 只是让你**写明**用哪种策略（不写时 GHC 按规则猜：Eq / Show 这类有 stock 派生的类优先 stock）。

GND 不是什么类都能派生。规则是：类方法里出现 newtype 的位置都要能 `coerce`。`traverse :: Applicative f => (a -> f b) -> t a -> f (t b)`
的返回值是 `f (t b)`，要把 `f (Array Pos b)` coerce 成 `f (Grid b)`，而 `f` 是任意的 Applicative，它的参数可能是 **nominal 角色**
（不允许 coerce），GHC 因此拒绝用 newtype 策略派生 `Traversable`。这时退回 stock 策略（`DeriveTraversable`），按构造器结构生成
`traverse f (Grid a) = Grid <$> traverse f a`。本仓库的 `Grid` 正好两种都用到了（§3.4）。

### 1.2 DefaultSignatures

类方法可以有缺省实现，但缺省实现只能用类本身的约束。`DefaultSignatures` 允许给缺省实现**单独一个更窄的签名**：

```haskell
class (Show e, Eq e, Typeable e) => Element e where
  name   :: e -> ElementName
  toCell :: e -> Cell
  default toCell :: Coercible e Int => e -> Cell      -- 只有「表示就是 Int」的 e 能用缺省
  toCell e = Custom (name e) (CustomState (coerce e))
```

- 方法本身的类型仍是 `toCell :: e -> Cell`，调用方看不到额外约束；
- 一个 instance 不写 `toCell` 时，GHC 用缺省实现，并在**这个 instance 处**检查 `Coercible e Int`；解不出来就是编译错误。

这正是 `Generic` 派生（aeson 的 `default toJSON :: (Generic a, ...) => ...`）用的机制，这里用它的最小形式：约束是 `Coercible`。

### 1.3 存在类型与 xmonad 风格的元素类

`data SomeElement = forall e. Element e => SomeElement e` 把「某个实现了 `Element` 的类型」装进一个统一类型（异构列表、注册表的值都要它）。
拆开盒子后编译器只知道 `e` 满足 `Element e`（以及超类 `Show` / `Eq` / `Typeable`），**不知道 e 具体是谁**。于是：

- **调方法**：直接调（`name e`、`caps e`），这是 OOP 式的动态分派，靠的是盒子里带着的实例字典；
- **拆箱成具体类型**：只能问运行时类型——`Typeable` 的 `cast :: (Typeable a, Typeable b) => a -> Maybe b`；
- **两个盒子比相等**：两边的类型各自不知道，先 `cast` 对齐类型，成功了再用该类型自己的 `Eq`（失败 = 类型不同 = 不等）。

本仓库有四个这样的盒子，和 xmonad 一一对应：

| xmonad | 本仓库 | 盒子里的类 | 拆箱 |
|--------|--------|------------|------|
| `Layout a` / `LayoutClass` | `SomeElement` / `Element` | 一种格子本体 | `fromElement` |
| `ModifiedLayout` 的修饰器 / `LayoutModifier` | `SomeModifier` / `Modifier` | 冰层、叠层 | `fromModifier` |
| （无；最接近的是 `ExtensibleState` 的状态值） | `SomeLevelElement` / `LevelElement` | 飞碟、皮带、传送门、地毯、地面层…… | `fromLevelElement` |
| `SomeMessage` / `Message` | `SomeMessage` / `Message` | 开放消息 | `fromMessage` |

组合方式也和 xmonad 一样，靠 **「盒子本身也是实例」**：

- `instance Element SomeElement`：装箱的元素还是元素，`name` / `toCell` / `caps` 转发给里面；
- `data Modified = Modified SomeModifier SomeElement` + `instance Element Modified`：修饰器套在元素外面，结果**又是一个元素**，
  所以能再装箱、再套一层（`modify (Ice 2) (modify chain e)`）。`caps` 按「修饰器先说，没意见再问里面」合成（挡交换任一层即挡、命中由最上一个有意见的层决定……）；
- 消息走 `handleMessage :: e -> SomeMessage -> Maybe SomeElement`：任何模块都能定义新消息类型（空 instance `Message`），收的一方用 `fromMessage` 认领，认不出来就 `Nothing`。

### 1.4 Functor / Foldable / Traversable 与 Monoid

这三个类描述「装着一些 `a` 的容器 t」能做什么，强度依次递增：

| 类 | 核心方法 | 能做什么 | 保证 |
|----|----------|----------|------|
| `Functor` | `fmap :: (a -> b) -> t a -> t b` | 逐格变换 | 形状不变；`fmap id = id`，`fmap (f . g) = fmap f . fmap g` |
| `Foldable` | `foldMap :: Monoid m => (a -> m) -> t a -> m` | 逐格统计（`length` / `sum` / `toList` / `any` / `elem` … 都由它推出） | 按固定顺序访问每个元素各一次 |
| `Traversable` | `traverse :: Applicative f => (a -> f b) -> t a -> f (t b)` | 带效果的逐格变换（状态、随机数、可能失败、收集日志） | 形状不变 + 顺序与 `Foldable` 一致；`mapAccumL` 是它在「状态」上的特例 |

`Foldable` 的 `foldMap` 要一个 **Monoid**（有结合律的 `<>` 和单位元 `mempty`）：每格映射成一份「小结果」，再用 `<>` 合起来。
`Sum Int`（加法）、列表（拼接）、本仓库的 `Counts`（逐键相加、`mempty` = 什么都没计）都是 Monoid。
`Array i` 本身就有这三个实例（按下标顺序，二维下标 `(行, 列)` 即行主序），所以 `Grid` 直接复用。

## 2. 为什么用在这里

挑选标准是：**现有代码已经在手写这个抽象**，换成语言机制后少一处可能写错的地方。逐个看：

- **GND**：`ElementName` / `CustomState` 的 `Show` 是手写的一行转发 `showsPrec d (ElementName s) = showsPrec d s`，`IsString` 也是 `fromString = ElementName`。
  这正是 newtype 策略的定义。手写版的风险是改的时候漏掉 `showList` / 写错优先级；派生版由编译器保证与 `String` / `Int` 完全相同。
- **DefaultSignatures**：六个元素的 `toCell` 都是 `Custom "名字" (CustomState k)`，而**名字在 `name` 里已经写过一遍**。两处字符串手动保持一致，
  写错一个字母（`"magic_stone"` vs `"magicstone"`）就是一个解码不回来的格子。缺省实现让名字只出现在 `name` 里。
- **存在类型**：三个盒子的 `Eq` 都是同一行 `maybe False (== b) (cast a)`，两个盒子的 `Show` 是同一个「标签 名字 值」格式；收成 `sameTypeEq` / `showsBoxed`，
  并把「为什么相等要靠 cast」「为什么 Modified 能嵌套」写进文档。这一项代码改动小，主要价值在讲清楚。
- **Grid**：盘面已经有 `mapBoard`（就是 `fmap`）、`boardCells`（就是 `toList`）、注册表里两个「数满足条件的格 / 按权重求和」的列表推导（就是 `foldMap`），
  以及 `randomBoardSized` 里一个手写的「带生成器状态逐格生成」的递归（就是 `mapAccumL`）。容器参数化以后这些都由标准实例给出。
- **Monoid**：`Counts` 早就有 `Semigroup` / `Monoid` 实例（`<>` 在连锁里到处用），但 `Cascade.hitsOn` / `withDrained` 还在用 `foldl` 逐个 `bumpCount` 进累积器。
  「每格一份计数再合并」就是 `foldMap`。

### 没选的方向

- **DerivingVia 给 `Counts` 派生 Monoid**：可以写一个 `newtype SparseSum k = SparseSum (Map k Int)` 带「逐键相加并去零」的实例，再 `deriving (Semigroup, Monoid) via SparseSum CounterKey`。
  但全仓库只有 `Counts` 一个用户，多一个类型只为派生一次，属于为展示而展示；现在的两行手写实例更直白。
- **`Score` 改 newtype + `Sum` 派生**：`type Score = Int` 在 src / app / web / 测试里有几百处当 `Int` 用，改动面和收益不成比例。
- **`CascadeTally` 做成 Monoid**：其中「最大波次」的合并（`combineCombo`）依赖左右顺序且不满足结合律，硬做成 Monoid 会违反定律。
- **`MBoard`（`Array Pos (Maybe Cell)`）也换成 `Grid`**：`Array` 本来就有这三个实例（`toM = fmap Just . boardArray` 早就在用 `fmap`），再包一层没有收益。

## 3. 改动前后

### 3.1 名字 newtype：`Match3.Types.Name`

改动前：

```haskell
newtype ElementName = ElementName { unElementName :: String }
  deriving (Eq, Ord)

instance Show ElementName where
  showsPrec d (ElementName s) = showsPrec d s

instance IsString ElementName where
  fromString = ElementName

newtype CustomState = CustomState { unCustomState :: Int }
  deriving (Eq, Ord)

instance Show CustomState where
  showsPrec d (CustomState n) = showsPrec d n
```

改动后（`DerivingStrategies` + `GeneralizedNewtypeDeriving`）：

```haskell
newtype ElementName = ElementName { unElementName :: String }
  deriving newtype (Eq, Ord, Show, IsString)

newtype CustomState = CustomState { unCustomState :: Int }
  deriving newtype (Eq, Ord, Show)
```

`IsString String` 的实例是 `instance a ~ Char => IsString [a]`，`fromString = id`，coerce 过来正好是 `ElementName`。
`show` 的输出逐字不变（`Custom "bubble" 1`、`showsPrec 11 (CustomState (-1))` = `(-1)`），金标准 3373 行逐字节相同。

### 3.2 缺省 `toCell`：`Match3.Element.Class` 与六个内置元素

改动前（以泡泡为例，六个元素同样的模式）：

```haskell
newtype Bubble = Bubble Int
instance Element Bubble where
  name _ = "bubble"
  toCell (Bubble k) = Custom "bubble" (CustomState k)   -- 名字第二次出现
  caps _ = ...
```

改动后：

```haskell
-- Class.hs
  toCell :: e -> Cell
  default toCell :: Coercible e Int => e -> Cell
  toCell e = Custom (name e) (CustomState (coerce e))

-- Collectible.hs
instance Element Bubble where
  name _ = "bubble"
  -- toCell：缺省实现（Int newtype → Custom (name e) (CustomState n)，见 Element 类）
  caps _ = ...
```

用缺省的：毛球 `Fuzzball`、泡泡 `Bubble`、变色龙 `Chameleon`、果冻 `Jelly`、魔法地格 `MagicGround`、魔法石 `MagicStone`。
没用的：`StoneE` / `ChestE` / `HoneyE` / `CakeE` / `SafeE` 表示也是 `Int`，但写回的是内置构造器（`Stone n`），保留自己的 `toCell`；
雪怪 `SnowBoss` 四个字段打包成一个 `Int`，手写；其余元素表示不是 `Int`，必须手写（不写就编译不过，见 §4）。

### 3.3 存在类型：`Match3.Element.Class`

改动前，三处各写一遍：

```haskell
instance Eq SomeElement where
  SomeElement a == SomeElement b = maybe False (== b) (cast a)
instance Show SomeElement where
  showsPrec d (SomeElement e) =
    showParen (d > 10) (showString "SomeElement " . showsPrec 11 (name e) . showChar ' ' . showsPrec 11 e)
-- SomeModifier、SomeLevelElement 的 Eq 同一行；SomeModifier 的 Show 同一格式
```

改动后：

```haskell
sameTypeEq :: (Typeable a, Typeable b, Eq b) => a -> b -> Bool
sameTypeEq a b = maybe False (== b) (cast a)

showsBoxed :: Show v => String -> ElementName -> v -> Int -> ShowS
showsBoxed tag n v d =
  showParen (d > 10) (showString tag . showChar ' ' . showsPrec 11 n . showChar ' ' . showsPrec 11 v)

instance Eq SomeElement where
  SomeElement a == SomeElement b = sameTypeEq a b
instance Show SomeElement where
  showsPrec d (SomeElement e) = showsBoxed "SomeElement" (name e) e d
```

`sameTypeEq` 的签名本身就是说明：`a`、`b` 是两个**独立**的类型变量（两个盒子里各自的类型），只要求 `b` 有 `Eq`、两边都 `Typeable`。
`SomeLevelElement` 的 Show 是「值本身的 Show」（不带标签），所以只共用 Eq。

### 3.4 盘面 `Grid`：`Match3.Types.Board`

改动前：

```haskell
newtype Board = Board (Array (Int, Int) Cell)
  deriving (Eq)
instance Show Board where
  showsPrec d b = showsPrec d (boardRows b)

boardCells :: Board -> [Cell]
boardCells (Board a) = elems a

mapBoard :: (Cell -> Cell) -> Board -> Board
mapBoard f (Board a) = Board (fmap f a)
```

改动后（`DeriveTraversable` + `DerivingStrategies` + `GeneralizedNewtypeDeriving`）：

```haskell
newtype Grid a = Grid (Array Pos a)
  deriving newtype (Eq, Functor, Foldable)   -- 复用 Array 的实例
  deriving stock (Traversable)               -- newtype 策略做不了（§1.1 的角色问题）

type Board = Grid Cell

instance Show a => Show (Grid a) where
  showsPrec d g = showsPrec d (gridRows g)

boardCells :: Board -> [Cell]
boardCells = toList

mapBoard :: (Cell -> Cell) -> Board -> Board
mapBoard = fmap
```

调用处：

```haskell
-- Countdown.hs：逐格变换
tickCountdowns = mapBoard tickCell          -- 前
tickCountdowns = fmap tickCell              -- 后

-- Registry.hs：逐格统计（Foldable + Sum）
countElementWith reg n b = length [() | cell <- boardCells b, elementName reg cell == n]                     -- 前
countElementWith reg n = getSum . foldMap (\cell -> if elementName reg cell == n then Sum 1 else mempty)      -- 后
weighElementWith reg n b = sum [diffWeight (bodyOf reg cell) | cell <- boardCells b, elementName reg cell == n]                 -- 前
weighElementWith reg n = getSum . foldMap (\cell -> if elementName reg cell == n then Sum (diffWeight (bodyOf reg cell)) else mempty)  -- 后
```

带状态的逐格生成（`Random.hs`），这是 Traversable 真正省事的地方：

```haskell
-- 前：手写递归 + 按列数切行
randomBoardSized rows cols g0 =
  let (cells, g') = go (rows * cols) g0
  in (boardFromRows (chunk cols cells), g')
  where
    go 0 g = ([], g)
    go n g =
      let (c, g1) = randomColor g
          (rest, g2) = go (n - 1) g1
      in (mkGem c : rest, g2)

-- 后：先建形状（Grid ()），再把生成器当累积器穿过每一格
randomBoardSized rows cols g0 =
  let (g', b) = mapAccumL (\g () -> let (c, g1) = randomColor g in (g1, mkGem c)) g0 shape
  in (b, g')
  where
    shape = gridFromRows (chunk cols (replicate (rows * cols) ()))
```

随机数的消耗顺序必须一个不差（同一种子同一盘面，金标准靠它）。`Traversable` 的定律保证 `mapAccumL` 按 `Foldable` 的顺序（`Array` 的下标顺序 = 行主序）
每格恰好访问一次、形状不变，所以与旧递归逐个相同；形状仍由原来的 `chunk cols` 建，连 0 行 / 0 列的边角下标范围都与原来一致。
`classes_random_board_same_as_recursion` 在 30 个种子 × 5–10 的全部行列组合（另加 0×0、0×3、3×0、1×1）上比对盘面、行列数和推进后的生成器。

### 3.5 计数合并：`Match3.Board.Cascade`

```haskell
-- 前
hitsOn reg b = foldl (\h p -> bumpHit (counterWith reg (getCell b p)) h) noCounts
withDrained reg drained h = foldl (\hh (_, cell) -> bumpHit (counterWith reg cell) hh) h drained
bumpHit :: Maybe CounterKey -> Counts -> Counts
bumpHit (Just k) h = bumpCount k 1 h   -- 另有 Nothing / CountSafes / CountSpirits 三条原样返回

-- 后
hitsOn reg b = foldMap (hitOf . counterWith reg . getCell b)
withDrained reg drained h = h <> foldMap (hitOf . counterWith reg . snd) drained
hitOf :: Maybe CounterKey -> Counts
hitOf (Just k) = singleCount k 1       -- 另有三条 = mempty
```

等价的理由：`Counts` 是**交换**幺半群（逐键整数加法），且不存 0（两份计数相等 ⟺ 每个键的个数相等），
所以「从左到右逐个加进累积器」和「每格一份、按任意结合方式合起来」结果相同。`Counts` 的结合律 / 交换律 / 单位元本来就有性质测试（`Spec.Properties` 的 Counts 代数），
`classes_foldMap_counts_same_as_foldl_bump` 再直接对照新旧两种写法。

## 4. 编译器 / 类型类能挡住哪些错误

| 写法 | 改动前 | 改动后 |
|------|--------|--------|
| 新元素 `data Pair = Pair Int Int`，instance 里忘了写 `toCell` | `-Wmissing-methods` 警告（网页版 `-Werror` 下是错误，桌面库只是警告），运行时一调 `toCell` 就崩 | 编译错误：`Couldn't match representation of type ‘Pair’ with that of ‘Int’ arising from a use of ‘$dmtoCell’` |
| Int newtype 元素的 `toCell` 里名字写错（`"magicstone"`） | 编译通过，格子解码不回来（落到惰性占格） | 用缺省时名字只在 `name` 里写一次，不存在第二份 |
| 名字 newtype 的 Show 改坏（漏 `showList`、优先级写错） | 只能靠快照发现 | 派生的就是 `String` / `Int` 的实例，没有可写错的代码 |
| 盘面逐格变换时改了形状 / 漏格 / 重复访问 | 手写递归里可能发生（`go` 的计数、`chunk` 的切法） | `fmap` / `traverse` / `mapAccumL` 的类型 `t a -> t b` 加上定律保证形状不变、每格一次 |
| 想对 `Grid` 用 newtype 策略派生 `Traversable` | — | 编译错误（角色检查）；这是 GHC 在保护 `coerce` 的安全性，改用 stock |

第一行写成了测试 `classes_default_toCell_needs_coercible`：`test/Spec/Classes.hs` 和 `Spec.Phase` 一样用 `-fdefer-type-errors` 把这个类型错误推迟到运行时，
测试求值 `toCell (Pair 1 2)`，断言抛出 `TypeError` 且消息点名 `Couldn't match representation of type` 和 `Pair`。
这个模块另加了 `-fno-defer-out-of-scope-variables`：拼错 / 漏导入的名字仍是编译错误，不会也被推迟成运行时异常（`-fdefer-type-errors` 默认会连带推迟它们）。

## 5. 取舍

- **行为不变、零开销**。GND 与 `coerce` 都在编译期消解；`Grid` 是 newtype，`fmap` / `foldMap` 就是 `Array` 的实例。验证：金标准 3373 行、元素查询快照 1666 行
  重新生成后与入库文件 `cmp` 逐字节相同；原有 396 个测试全过，新增 8 个。
- **缺省 `toCell` 的代价是「悄悄生效」**。任何 `newtype X = X Int` 的元素，忘了写 `toCell` 都会得到 `Custom (name x) (CustomState n)`，而不是编译错误。
  对 `StoneE` 这类写回内置构造器的元素，忘写就是一个错误编码。缓解：注册表的 `qc_registry_decode_roundtrip` 检查任意格「解码再写回」不变
  （1000 个随机格，覆盖全部内置构造器），`classes_default_toCell_same_as_handwritten` 逐个锁定六个用缺省的元素和 `StoneE`，金标准 / 元素查询快照
  兜住整局行为；instance 里也留了一行注释标明用的是缺省。如果以后觉得这种隐式太危险，可以去掉缺省、改导出一个显式 helper
  `customIntCell :: (Element e, Coercible e Int) => e -> Cell`，每个元素写 `toCell = customIntCell`——多一行，但不再隐式。
- **`type Board = Grid Cell` 是同义词**，不是新的 newtype。好处是所有 `Board` 签名、`boardAt` / `boardSet` 等函数原封不动；代价是以后不能再给 `Board` 单独写一个
  与 `Grid Cell` 不同的实例（目前全仓库没有以 `Board` 为实例头的实例，原来的 `Show Board` 变成了 `Show (Grid a)`）。
- **`Foldable` 只给格子，不给坐标**。很多遍历是 `[p | p <- boardPositions b, isX (getCell b p)]` 这种「要坐标」的形式（Grass、Snail、Shuffle、几个内置元素等约二十处），
  `Foldable` 帮不上；要做得引入 `FoldableWithIndex`（`lens` / `indexed-traversable`）或自己写 `ifoldMap`，为此加依赖或新类不值得，保持原样。（后来第 7 项手写了 `ifoldMap` / `ifoldr` / `positionsWhere`，不加依赖、不建类，见 [07-网格几何.md](07-网格几何.md) §1.2。）
- **`countElementWith` 用 `foldMap` 到 `Sum` 而不是 `length . filter`**：两种都行；选 `foldMap` 是为了和 `weighElementWith`（按权重求和）同一个形状，两行一眼能对上。
- **存在类型这一项代码改动最小**：只是把重复的一行收成 helper。真正值得看的是 §1.3 的对照表和「盒子本身也是实例」的组合方式，
  它决定了冰 + 叠层 + 本体能任意嵌套，而主流程只认 `SomeElement` 一个类型。
- **语言扩展**：只在用到的模块里开（`DerivingStrategies`、`GeneralizedNewtypeDeriving`、`DeriveTraversable`、`DefaultSignatures`），没改默认语言；
  网页版（Haskell2010 + `-Wall -Werror`）照常编译。
