## 0. 一句话

把**连锁**（一步棋里「消除 → 下落 → 补子 → 飞碟吸收 → 再消除……」那一段）写成只依赖三个**能力类**的程序：
补子（唯一消耗随机数的地方）、关卡级钩子、发出一轮回放。程序本身不知道随机数和状态放在哪里；
同一个程序交给**纯解释器**就是原来的结果，交给**追踪解释器**就额外得到一份事件日志，测试里再把它解释成一棵 **free monad** 指令树跑第三遍——三种跑法结果逐项相同。

## 1. 这些特性是什么

### 1.1 效果 = 「除了算出返回值以外，还做了什么」

纯函数只能通过参数和返回值和外界打交道。连锁要做三件「额外的事」：

| 效果 | 改写前怎么做 | 改写后 |
|------|------------|--------|
| 消耗随机数（补子） | 参数里收 `g`，返回值里带回 `g'`，调用方接着传 | `refillHoles :: RefillPolicy -> Stage 'Fallen -> m (Stage 'Full)` |
| 读写关卡级钩子（飞碟吸收会推进飞碟的状态） | 参数里收 `hooks`，返回 `hooks'` | `currentHooks :: m LevelHooks`、`absorbHooks :: Board -> m [Pos]` |
| 记录回放（每一轮一条 `CascadeWave`） | 参数里带反向累积器 `wavesRev`，收尾时 `reverse` | `emitWave :: CascadeWave -> m ()` |

「手工传递」本身就是 State / Writer monad 的展开形式。把它收进 monad 后，传错一个版本（用了 `g1` 而不是 `g2`、用了旧的 `hooks`）在写法上就不可能了。

### 1.2 mtl 风格：能力类（tagless final）

mtl 的 `MonadState s m` 说的是「m 里能读写一个 s」，**不说 m 是什么**。程序写成 `MonadState s m => ... -> m a`，
运行时再选具体的 monad（`State s`、`StateT s IO`……）。这个风格也叫 **tagless final**：程序是「对任意解释器多态的值」。

本仓库没有直接用 `MonadState`，而是按同样的套路**自定义了三个领域能力类**：

```haskell
class Monad m => MonadRefill m where
  refillHoles :: RefillPolicy -> Stage 'Fallen -> m (Stage 'Full)

class Monad m => MonadLevelHooks m where
  currentHooks :: m LevelHooks
  absorbHooks  :: Board -> m [Pos]

class Monad m => MonadWaves m where
  emitWave :: CascadeWave -> m ()

type MonadCascade m = (MonadRefill m, MonadLevelHooks m, MonadWaves m)   -- ConstraintKinds
```

为什么不用 `MonadState (g, LevelHooks, [CascadeWave]) m`：

- mtl 的 `MonadState s m` 有函数依赖 `m -> s`，一个 monad 只能有一种状态；三种效果要么塞进一个元组（程序就知道了状态的布局），要么叠三层 transformer 再 `lift`；
- 更要紧的是，`MonadState` 只说「能读写」，追踪解释器拦不住「这次 `put` 是在补子」——它只看得到状态变了。领域能力类的方法**本身就是事件**，
  追踪解释器在 `refillHoles` 里就知道「补了哪些格」，在 `absorbHooks` 里就知道「这一拍吸走了什么」；
- 签名更会说话：`settleRoundM :: (MonadRefill m, MonadLevelHooks m) => ...` 一眼看出这一步会补子、会读钩子、**不会**发回放。

随机数能力也可以写成 `MonadRandom` 风格的通用接口（`getRandomR`，或 `withGen :: (forall g. RandomGen g => g -> (a, g)) -> m a`）。
这里选了领域方法 `refillHoles`，因为连锁里只有补子这一处用随机数，按领域命名能让追踪日志记到「补进的格子」，也让以后「用固定脚本补子」的测试解释器只实现一个方法。

### 1.3 解释器

| 解释器 | 定义 | 用途 |
|--------|------|------|
| `PureCascade g` | `newtype PureCascade g a = PureCascade (State (PureSt g) a)`，状态 = 生成器、钩子、反向累积的回放；`deriving newtype (Functor, Applicative, Monad)`（第 2 项的 GND） | 生产路径：全部 `...With` 入口 |
| `TracedCascade g` | `newtype TracedCascade g a = TracedCascade (StateT [CascadeLog] (PureCascade g) a)` | 调试 / 测试：每个能力先交给里层纯解释器执行，再记一条 `CascadeLog` |
| `Free CascadeF`（测试里） | 手写 free monad，每个能力变成一条指令 | 证明程序与编码无关；见 §1.4 |

追踪解释器是**叠在**纯解释器上的（monad transformer）：

```haskell
instance RandomGen g => MonadRefill (TracedCascade g) where
  refillHoles pol fallen = TracedCascade $ do
    filled <- lift (refillHoles pol fallen)              -- 交给里层：真的补子、真的消耗随机数
    let holes = [p | (p, Nothing) <- assocs (stageGrid fallen)]
    record (LogRefill [(p, boardAt (stageGrid filled) p) | p <- holes])   -- 再记一笔
    pure filled
```

所以它和纯解释器的结果**按构造**相同（测试仍然逐项比对）。

### 1.4 free monad / operational：另一种「程序 + 解释器」

free monad 把程序表示成**数据**：每种效果一条指令，后面接一个「拿到结果之后怎么继续」的函数（续体）。

```haskell
data CascadeF next
  = RefillF RefillPolicy (Stage 'Fallen) (Stage 'Full -> next)
  | HooksF  (LevelHooks -> next)
  | AbsorbF Board ([Pos] -> next)
  | EmitF   CascadeWave next
  deriving Functor

data Free f a = Done a | Step (f (Free f a))          -- 程序 = 指令树
instance Functor f => Monad (Free f) where
  Done a  >>= k = k a
  Step op >>= k = Step (fmap (>>= k) op)
```

解释器就是对这棵树的递归：

```haskell
interpret hooks g prog = case prog of
  Done a -> (a, hooks, [], g)
  Step (RefillF pol s k) -> let (s', g') = refillStage pol g s in interpret hooks g' (k s')
  Step (HooksF k)        -> interpret hooks g (k hooks)
  Step (AbsorbF b k)     -> let (ps, hooks') = onAbsorb hooks b in interpret hooks' g (k ps)
  Step (EmitF w next)    -> let (a, h, ws, g') = interpret hooks g next in (a, h, w : ws, g')
```

`operational` 包是同一思路的变体：指令写成 GADT（`data CascadeI a where Refill :: ... -> CascadeI (Stage 'Full)`），不需要 `Functor`，续体由库统一管理。

**两种风格可以互相转换**：只要给 `Free CascadeF` 写三个能力类的实例（每个方法 = 一条指令），任何 `MonadCascade m => m a` 的程序就自动变成一棵指令树。
`test/Spec/Effects.hs` 正是这么做的：**同一份** `cascadeMatchesM` 等程序，不改一个字，用 free monad 解释器又跑了一遍。

| | 能力类（tagless final，本仓库主体） | free / operational |
|---|---|---|
| 程序是什么 | 对 `m` 多态的函数 | 一棵指令树（数据） |
| 加一个解释器 | 写一个 newtype + 几个实例 | 写一个对树的递归函数 |
| 加一种效果 | 加一个类（已有程序不受影响，只有用到它的函数约束变多） | 给指令类型加构造器（所有解释器都要处理） |
| 运行时开销 | 实例在编译期确定，GHC 能特化 / 内联到接近手写 | 每条指令分配一个节点，`>>=` 左结合时是平方复杂度（要 Codensity 等技巧） |
| 检查 / 改写程序 | 做不到（程序不是数据） | 理论上可以，但续体依赖前面的结果，实际只能「边跑边看」 |
| 依赖 | `transformers`（GHC 自带） | `free` 包，或像测试里那样手写 20 行 |

本仓库选能力类做主体：生产路径要的是零开销和「签名说明用到的效果」，free 的「程序是数据」在这里用不上（连锁的每一步都依赖上一步的盘面）。

## 2. 为什么用在这里

连锁核心正好是「纯计算里夹着手工传递的效果」最集中的地方。改写前 `cascadeMatchesFromWith` 的循环带着 **10 个参数**：

```haskell
go pref g b cells score maxW hits hooks clearedRev wavesRev
```

其中 `g`、`hooks`、`wavesRev` 三个纯粹是在搬运效果；每一轮里生成器经过 `g → g1 → g2`、钩子经过 `hooks → hooks'`，
`settleRound` / `absorbRound` 都要把 `g` 传进去、把 `g'` 带出来。种子起手、皮带后、倒计时又各有一份同样的搬运。

为什么是连锁、而不是整步结算（`Game.Resolve.resolveMoveWith`）：

- 连锁里的效果**真的交错**：补子消耗随机数、补完立刻问飞碟吸不吸、吸了又要补子……顺序就是行为（金标准锁死了随机数的消耗顺序）；
- 结算那一层主要是一串纯的 `let`（计数、目标、结局判定），只在最后的自动洗牌用一次 `gsGen`，改成 monad 收益很小；
  它通过 `runEndTable` 消费各段的 `CascadeRun`，入口签名不变，这一层就不用动；
- 范围可控：只动 `Board/Cascade.hs` 一个文件的内部，外部 API 零改动。

## 3. 改动前后

### 3.1 一轮：`settleRound` → `settleRoundM`

改动前：

```haskell
settleRound :: RandomGen g => Registry -> LevelHooks -> g -> Stage 'Full -> (Stage 'Cleared, Int, [Pos]) -> Int -> (Round, g)
settleRound reg hooks g before (holes, n, pos) w =
  let (fallen, drained) = fallStage reg hooks holes
      (after, g') = refillStage (activeRefill reg hooks) g fallen
      ...
  in (Round wave after n (...) sites, g')
```

改动后：

```haskell
settleRoundM :: (MonadRefill m, MonadLevelHooks m) => Registry -> Stage 'Full -> (Stage 'Cleared, Int, [Pos]) -> Int -> m Round
settleRoundM reg before (holes, n, pos) w = do
  hooks <- currentHooks
  let (fallen, drained) = fallStage reg hooks holes
  after <- refillHoles (activeRefill reg hooks) fallen
  ...
  pure (Round wave after n (...) sites)
```

第 1 项的阶段标签原样保留：`refillHoles` 只收 `Stage 'Fallen`，没下落就补子仍然编译不过。

### 3.2 匹配连锁的循环

改动前（节选）：

```haskell
go pref g b cells score maxW hits hooks clearedRev wavesRev
  | not (hasAnyMatchWith reg b) =
      CascadeRun b (CascadeTally ...) hooks (reverse wavesRev) g
  | otherwise =
      let (r1, g1) = settleRound reg hooks g bS cr wave
          (hooks', absorbed, g2) = absorbRound reg hooks g1 b1 (wave + 1)
      in case absorbed of
           Nothing -> go Nothing g2 b1 ... hooks' (posD : clearedRev) (rdWave r1 : wavesRev)
           Just (r2, nAbs) -> go Nothing g2 (rdAfter r2) ... hooks' (...) (rdWave r2 : rdWave r1 : wavesRev)
```

改动后：

```haskell
go pref b cells score maxW hits clearedRev
  | not (hasAnyMatchWith reg b) =
      pure (b, CascadeTally ...)
  | otherwise = do
      r1 <- roundM reg bS cr wave                 -- 沉降 + 补子 + 发出回放
      ...
      absorbed <- absorbRoundM reg b1 (wave + 1)  -- 吸收节拍（推进钩子；吸到了就再一轮）
      case absorbed of
        Nothing -> go Nothing b1 ... (posD : clearedRev)
        Just (r2, nAbs) -> go Nothing (rdAfter r2) ... (rdSites r2 : pos2 : posD : clearedRev)
```

剩下的累积器（清除格数、得分、最大波次、计数、清除格）都是**计数**，留在显式参数里：它们决定返回值，不是效果；
其中最大波次的合并不满足结合律（第 2 项 §2 讲过），也不适合塞进 Writer。

### 3.3 对外入口：纯解释器

```haskell
cascadeMatchesFromWith :: RandomGen g => Registry -> Int -> Maybe Pos -> LevelHooks -> g -> Board -> CascadeRun g
cascadeMatchesFromWith reg startW prefer hooks g b = runCascade hooks g (cascadeMatchesFromM reg startW prefer b)

runCascade :: LevelHooks -> g -> PureCascade g (Board, CascadeTally) -> CascadeRun g
runCascade hooks g m = ranToRun (runPureCascade hooks g m)
```

`cascadeSeedsWith` / `cascadeAfterWith` / `cascadeCountdownsTracedWith` / `stepCascadeAtWith` 同样各是一行。

### 3.4 追踪解释器的日志

```haskell
data CascadeLog
  = LogRefill [(Pos, Cell)]   -- 补子：补进的 (格, 新格子)，行优先
  | LogAbsorb [Pos]           -- 整轮吸收节拍：被吸走的格（空 = 这一拍没有吸收）
  | LogWave CascadeWave       -- 发出一轮回放

(run, logs) = runCascadeTraced hooks g (cascadeMatchesM reg Nothing b)
```

一次带飞碟的连锁，日志形如 `LogRefill […] , LogWave w1 , LogAbsorb [(3,4)] , LogRefill […] , LogWave w2 , LogAbsorb [] , …`：
哪一轮补了哪些格、飞碟在哪一拍吸了什么，按发生顺序一目了然。前端现在不用它（回放仍读 `crWaves`），它是给调试和测试的。

## 4. 编译器 / 类型能挡住什么

| 写法 | 改写前 | 改写后 |
|------|--------|--------|
| 用错生成器版本（把 `g1` 写成 `g`，同一批随机数用两次） | 编译通过，补子结果重复，只有金标准能发现 | 写不出来：程序里没有 `g` |
| 用了吸收前的旧钩子 | 编译通过，飞碟状态回退 | 写不出来：钩子只能经 `currentHooks` 读，读到的总是最新的 |
| 回放顺序弄反 / 漏记一轮 | 累积器 `reverse` 的位置写错就错 | `emitWave` 按发生顺序记（「只沉降」那一轮的条件发射是显式的 `when`） |
| 一个「只该补子、不该发回放」的辅助函数里发了回放 | — | `settleRoundM` 的约束里没有 `MonadWaves`，调 `emitWave` 是类型错误：`Could not deduce ‘MonadWaves m’ arising from a use of ‘emitWave’ from the context: (MonadRefill m, MonadLevelHooks m)` |
| 纯解释器之外的地方偷偷消耗随机数 | — | 连锁程序拿不到 `RandomGen` 的值，只能经 `refillHoles` |

`-Wredundant-constraints`（本仓库开着）还会反过来提醒：逐个写出的约束里有用不到的（例如写了 `MonadWaves m` 却没发回放）就是警告 `Redundant constraint: MonadWaves m`。
注意这个检查看不穿约束同义词：写 `MonadCascade m` 而只用到其中两种能力时**不会**警告，所以只读钩子 + 补子的 `settleRoundM` 特意逐个写出约束，用全三种的函数才写 `MonadCascade`。

## 5. 取舍

- **行为不变**：金标准 3373 行、元素查询快照 1666 行逐字节一致；原有 404 个测试全过。新增的 `Spec.Effects` 在全部战役关卡 × 2 个种子 × 3 个盘面（共一百多个用例）上，
  对七个连锁入口与单轮比对改写前的逐字副本：终盘、计数、每一轮回放、推进后的关卡级元素、生成器（`show`），倒计时另比步末记录。
  （逐字副本后来在死代码清理中删除，这组对照改为每个入口一个写死的摘要 `effects_entries_pinned`，见[旧副本对照的去留](../testing.md#旧副本对照的去留)。）
  用例确实走到了飞碟吸收、补子、步末后「补了子但不记回放」三种节拍（测试里有断言）。
  另外做过一次变异检查：把吸收轮的波次从 `wave + 1` 改成 `wave + 2`，三个效果测试和金标准都立刻失败。
- **严格度**：用的是 `Control.Monad.Trans.State.Strict`（只对状态元组严格，不强制里面的值），生成器、钩子仍按需求值，与原来的 `let` 链一样惰性；
  没有给状态字段加 `!`，避免提前求值改变任何可观察行为。
- **新依赖只有 `transformers`**：GHC 自带的引导库（桌面 GHC 9.14.1 与 wasm 工具链里都有），不需要下载；没用 `mtl`（自定义能力类不需要 `MonadState`），也没加 `free` 包（测试里手写）。
- **性能**：`PureCascade` 是 `State` 上的 newtype，GND 派生的 `Monad` 实例就是 `State` 的；整套测试耗时与改写前同量级（约 12–13 秒）。
  连锁每步最多几十轮，monad 的那点间接调用不可见。若以后在热点里用，可以给 `runCascade` 加 `SPECIALIZE` 或改成 CPS。
- **只改了连锁，没改整步结算**：理由见 §2。`Game.Resolve` 的计数 / 结局部分是纯 `let`，硬改成 monad 只是换写法；
  如果以后要把自动洗牌、步末效果也纳入同一套能力，`resolveMoveWith` 可以在同一个解释器里调用这些程序，再加一个 `MonadShuffle` 能力。
- **`CascadeWave` 挪了模块**：效果层（`Effect`）需要它，而 `Cascade` 依赖效果层，只能拆到 `Board/Wave.hs`；`Cascade` 原样再导出，所有 import 不变。
- **追踪解释器目前只给测试 / 调试用**，前端和网页版的回放仍读 `crWaves`。把日志接进开发者面板是自然的下一步，但不在本项范围。
- **语言扩展**：`ConstraintKinds`（约束同义词）、`DataKinds`（`Stage 'Fallen`）、`DerivingStrategies` + `GeneralizedNewtypeDeriving`（解释器的 Monad 实例）；
  测试另用 `RankNTypes`（把多态程序放进列表）、`DeriveFunctor`、`FlexibleInstances`（`instance MonadRefill (Free CascadeF)`）。都只在用到的模块里开。

|--------|------|-----------|
| 一种效果的接口 | `class Monad m => MonadX m where op :: ... -> m r` | `Board/Effect.hs` 三个能力类 |
| 多个能力合成一个约束 | `type MonadCascade m = (A m, B m, C m)`（`ConstraintKinds`） | `MonadCascade` |
| 程序只依赖能力 | `f :: (MonadRefill m, MonadLevelHooks m) => ... -> m r` | `settleRoundM` |

| 在解释器上叠一层行为 | `newtype T g a = T (StateT Log (P g) a)`，方法里先 `lift` 再记录 | `TracedCascade` |
| 程序 = 数据 | `data F next = ...` + `data Free f a = Done a \| Step (f (Free f a))` | `test/Spec/Effects.hs` |
| 能力类程序 → 指令树 | 给 `Free F` 写能力类实例：每个方法 = `liftF` 一条指令 | `test/Spec/Effects.hs` |
| 把多态程序放进列表 | `newtype Prog = Prog (forall m. MonadCascade m => m a)`（`RankNTypes`） | `test/Spec/Effects.hs` |
| 证明新旧路径逐项相同 | 改写前代码的逐字副本 + 全关卡用例比对（含生成器 `show`）；副本删除后改为写死的摘要 | `effects_entries_pinned`（原 `Spec.Support.LegacyCascade`） |
