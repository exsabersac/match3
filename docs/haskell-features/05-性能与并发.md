## 1. 这些特性是什么

### 1.1 boxed 与 unboxed：`Array` 和 `UArray`

`Data.Array.Array i e` 的每个元素是一个**指针**，指向堆上的值或 thunk（元素是惰性的）；读一格要解引用、可能还要求值。
`Data.Array.Unboxed.UArray i e` 只能放 `Int` / `Bool` / `Char` / `Double` 这类原始类型，元素直接存成机器字，
整张数组是一块连续内存，**元素严格**（建数组时全部算好）。代价是不能放任意类型、也不能当惰性记忆表用。

本仓库的盘面是 `Array Pos (Maybe Cell)`——`Cell` 是代数类型，没法 unboxed。但匹配只关心「这一格参与匹配的颜色是什么，或者不参与」，
这可以编码成一个 `Int`（颜色的 `fromEnum`，不参与是 `-1`），于是一次扫描可以先投影出一张 `UArray Pos Int`。

### 1.2 `ST`：在纯函数里用可变状态

`ST s a` 是「只在局部可变」的计算：里面可以 `newArray` / `readArray` / `writeArray`，跑完用 `runST`（或直接返回数组的 `runSTArray`）
得到一个普通的纯值。关键在类型：

```haskell
runST      :: (forall s. ST s a) -> a
runSTArray :: (forall s. ST s (STArray s i e)) -> Array i e
```

参数是 **rank-2** 的：调用方不能选 `s`，所以带 `s` 的东西（`STArray s …`、`STRef s …`）不可能出现在结果类型 `a` 里——
可变数组**出不了** `runST`，外面看到的只有冻结后的不可变结果。`runSTArray` 在最后直接把可变数组「冻结」成 `Array`，不复制。
同一个输入永远给出同一个输出，所以它仍然是纯函数，可以放在纯接口背后、用纯的旧实现对照测试。

### 1.3 严格性与 unboxing（和第 4 项的关系）

第 4 项讲的是「惰性堆 thunk」；这里是另一面：**热路径上的中间结构**。旧的匹配扫描每格要
`getCell`（`Array` 取指针）→ `matchColorWith`（按名字查注册表、组合本体与叠层）→ 比较 `Maybe Color`；
提示搜索每个候选交换还要 `swapCells`（两次整盘 `//` 复制）。现在把注册表查询**提前到每格一次**，结果放进 unboxed 数组，
之后的扫描只做 `Int` 比较。`codesHaveRun` 的累积参数 `go prev n` 是严格使用的 `Int`，`-O1` 下 GHC 的严格性分析与
worker/wrapper 变换可以把它们拆箱成 `Int#`（本项没有逐个核对 Core，量出来的效果见 §4：总分配少了 35 %）。

### 1.4 `forkIO` 与 STM

`forkIO :: IO () -> IO ThreadId` 起一个绿色线程（GHC 运行时调度到 `-N` 个系统线程上）。线程之间共享状态用 STM：

- `TVar a`：事务变量；`atomically` 里的一串读写是**原子**的——要么全部生效，要么（冲突时）整个事务自动重跑；
- `TMVar a`：要么空、要么有一个值；`takeTMVar` 在空时阻塞（事务里的 `retry`），`putTMVar` 在满时阻塞。

`parallelForce` 只用这两样：一个 `TVar Int` 记「下一个要领的任务下标」，每个任务一个 `TMVar` 结果槽。
纯计算本身是确定的，并行只改变**什么时候在哪个核上算**，所以只要拼回的顺序固定，结果就与串行逐项相同。

## 2. 为什么用在这里

**先量再改。** 用 `stack build --profile` 做剖析构建，`-fprof-auto-top` 编译金标准生成器，结果（改写前）：

| 成本中心 | 继承时间占比 | 备注 |
|---------|-----------:|------|
| `findMatchRunsWith` | ≈ 42.5 % | 连锁每轮、开局、洗牌都要扫 |
| `groupGemRunsWith` | ≈ 40 % | 上面两者的内层 |
| `hasAnyMatchWith` | ≈ 35.7 % | 调用 24 万次（提示搜索的每个候选、采样器、洗牌） |
| `matchColorWith` | ≈ 27 % | **调用 4668 万次**：每格行一遍、列一遍 |
| `findHintWith` | ≈ 6 % | 每个候选 `swapCells` 两次整盘复制 |
| `applyGravityWith` | ≈ 2.4 % | |
| `refill` | ≈ 0.6 % | |
| `boardSet` | ≈ 0.1 % | |

（各行是继承时间，互相包含，不能相加。）所以第一刀落在匹配扫描上：问注册表的次数从「每次扫描每格两遍」降到「每次扫描每格一遍」，
提示搜索不再复制盘面。

**重力是「ST 的典型形状」，但不是热点。** 每列按固定格切段、段内实格落到底——旧写法为每列建列表、切段、拼接，最后 `array` 一遍；
这正是「就地双指针压实」最自然的场景，所以用它展示 `runSTArray`。剖析里它只占 2.4 %，§4 的数据也如实显示整体收益在噪声范围内。

**金标准是现成的确定性批量模拟。** `golden.txt` 的 3373 行来自 38 关 × 种子 1 / 2 各走 15 步、2 个每日开局、几段手工局面，
以及第 39 关起每关一块的投影——各段只依赖固定的关卡与种子，互不共享状态，天然可以并行。它也是测试套件里最慢的用例（单个 10 s）。

**没有动的地方（以及原因）：**

- **`refill` / `boardSet`**：合计不到 1 %，改了也量不出来。
- **注册表查找**：改写后的剖析比较平坦，剩下排在前面的是 `bodyOf` / `caps` / `levelNameOf` 和按名字比较字符串的 `eqString`——
  注册表按元素名字（`String`）查能力。这是**下一个热点**，但要动就得改注册表的表示（名字 → 编号或 `Map`），
  牵涉第 2 项的元素类框架和网页版，不属于「局部可变」这一项，这里只记下来。
- **提示搜索用 ST 就地交换**：试过（`demo/MatchBench.hs` 的 `hint-st`），和纯函数写法一样快，没有采用（§5）。
- **游戏里的并发**：游戏逻辑是纯的单线程状态机，网页版跑在 wasm 单线程里，没有可并行的落点；并发只用在测试的批量模拟上。
- **`criterion`**：不进依赖；微基准用 `getCPUTime`，整体用 `time` 计墙钟，数字都可以用文档里的命令复现。

## 3. 改动前后

### 3.1 匹配码：每格只问一次注册表

```haskell
-- 新（Match3.Board.Match）
matchCodesWith :: Registry -> Board -> UArray Pos Int
matchCodesWith reg b =
  let arr = boardArray b
  in listArray (A.bounds arr) [maybe noCode fromEnum (matchColorWith reg cell) | cell <- elems arr]
```

连线扫描在码上找「同码且 ≥ 3」的段（码 < 0 打断），顺序与旧写法相同（先行后列、各自按下标升序）：

```haskell
-- 旧：每条线 groupGemRunsWith（逐格 matchColorWith），再滤出长度 ≥ 3 的段；行一遍、列一遍
findMatchRunsWith reg b = filter ((>= 3) . length . runPos) (hRuns ++ vRuns)
  where hRuns = [MatchRun col ps True | r <- rows, (col, ps) <- groupGemRunsWith reg b [(r, c) | c <- cols]]
        vRuns = [MatchRun col ps False | c <- cols, (col, ps) <- groupGemRunsWith reg b [(r, c) | r <- rows]]
-- 新：同样的循环，只是线上的「颜色」从码数组里读
findMatchRunsWith reg b =
  [MatchRun (toEnum k) ps True | r <- rows, (k, ps) <- codeRuns code [(r, c) | c <- cols]]
    ++ [MatchRun (toEnum k) ps False | c <- cols, (k, ps) <- codeRuns code [(r, c) | r <- rows]]
  where codes = matchCodesWith reg b
        code = (codes !)
```

`hasAnyMatchWith` 原来是 `not (null (findMatchRunsWith …))` 的形状，现在直接在码上逐行逐列跑 `codesHaveRun`，
不建 `MatchRun` 列表，找到第一条就停。

### 3.2 提示搜索：对调下标代替复制盘面

第 3 项起提示搜索已经是「局部检查」：交换后有匹配 ⇔ 没被触及的行 / 列原来就有三连，或被触及的行 / 列交换后有三连。
但「交换后」仍要 `swapCells b p1 p2`（复制整盘两次）再逐格问注册表。现在：

```haskell
codes = matchCodesWith reg b
rowHas = A.listArray (0, boardNRows b - 1) [codesHaveRun (map (codes !) (rowPs r)) | r <- rows] :: Array Int Bool
swapMakesMatch p1@(r1, c1) p2@(r2, c2) =
  let rs = nub [r1, r2]; cs = nub [c1, c2]
      at q | q == p1 = codes ! p2          -- 「换过之后」的码：两个下标对调着读
           | q == p2 = codes ! p1
           | otherwise = codes ! q
  in any (codesHaveRun . map at . rowPs) rs || any (codesHaveRun . map at . colPs) cs
       || or [rowHas A.! r | r <- rows, r `notElem` rs] || or [colHas A.! c | c <- cols, c `notElem` cs]
```

能这样做的前提是：**匹配只看每格自己的 `matchColorWith`**（与位置、邻格无关），所以「换两格」等于「换两格的码」。
`rowHas` / `colHas` 仍是第 4 项提过的**元素惰性 `Array`**——每行的结论用到才算、最多算一次；码数组本身是 unboxed、严格的。
两种数组各用在合适的地方：要按需求值的用 boxed，要紧凑快读的用 unboxed。

### 3.3 重力：`runSTArray` 里双指针压实

```haskell
-- 旧
applyGravityWith reg mb =
  let bnds@((r0, c0), (r1, c1)) = bounds mb
      rows = [r0 .. r1]
  in array bnds [((r, c), v) | c <- [c0 .. c1], (r, v) <- zip rows (colGravityWith reg [mb ! (r', c) | r' <- rows])]

-- 新
applyGravityWith reg mb = runSTArray $ do
  let bnds@((r0, c0), (r1, c1)) = bounds mb
  m <- newListArray bnds (elems mb)
  forM_ [c0 .. c1] $ \c -> do
    let fixedAt r = maybe False (gravityFixedCellWith reg) (mb ! (r, c))
        segments lo [] = [(lo, r1)]
        segments lo (r : rs) | fixedAt r = (lo, r - 1) : segments (r + 1) rs
                             | otherwise = segments lo rs
    forM_ (segments r0 [r0 .. r1]) (\(lo, hi) -> when (lo <= hi) (compactSegment m c lo hi))
  pure m

compactSegment :: forall s. STArray s Pos (Maybe Cell) -> Int -> Int -> Int -> ST s ()
compactSegment m c lo hi = go hi hi
  where
    go :: Int -> Int -> ST s ()
    go r w
      | r < lo = forM_ [lo .. w] (\k -> writeArray m (k, c) Nothing)   -- 段顶剩下的是空洞
      | otherwise = do
          v <- readArray m (r, c)
          case v of
            Just _ -> writeArray m (w, c) v >> go (r - 1) (w - 1)       -- 实格写到写指针处
            Nothing -> go (r - 1) w
```

读指针 `r` 自下而上，写指针 `w` 指向下一个该填的位置；因为 `w >= r` 恒成立，写不会覆盖还没读到的格，段内实格的相对次序不变——
与 `colGravityWith` 的「`replicate holes Nothing ++ map Just solids`」逐格相同。固定格的判断读的是**原盘** `mb`（固定格本身不会被移动）。
网页版是 Haskell2010：`compactSegment` 和内层 `go` 都写了类型签名（`forall s.` + `ScopedTypeVariables`），否则要开 `FlexibleContexts`。

### 3.4 金标准：切段 + STM 并行求值

```haskell
-- test/golden/Golden.hs
goldenLines = concat goldenSections
goldenSections =
  [ runGame ("L" ++ pad2 (li + 1) ++ " s" ++ show seed) (levelGame li seed) 15 | li <- [0 .. campaign38 - 1], seed <- [1, 2] ]
    ++ [ runGame ("D" ++ show seed) (newDailyGame (GameConfig 20 (goalScore 900)) seed) 10 | seed <- [20260929, 20260101] ]
    ++ [handmade, cascadeLines, levelLines, handmade2, seg5Lines]
    ++ seg6Blocks
```

```haskell
-- test/Spec/Support/Parallel.hs（节选）
parallelForce workers force xs = do
  let n = length xs
      tasks = listArray (0, n - 1) xs
  next <- newTVarIO 0
  slotList <- forM xs (const newEmptyTMVarIO)
  let slots = listArray (0, n - 1) slotList
      claim = atomically $ do                 -- 读出下标并加一：原子的，不会重领、不会漏
        i <- readTVar next
        if i >= n then pure Nothing else writeTVar next (i + 1) >> pure (Just i)
      worker = do
        mi <- claim
        case mi of
          Nothing -> pure ()
          Just i -> do
            let x = tasks ! i
            r <- try (evaluate (force x))   -- 在工人线程里算完，不是把 thunk 交回主线程
            atomically (putTMVar (slots ! i) (fmap (const x) r))
            worker
  replicateM_ (max 1 (min workers n)) (forkIO worker)
  forM slotList (\s -> atomically (takeTMVar s) >>= either throwIO pure)   -- 按下标顺序取回
```

要点：

- **领任务是动态的**：段的大小差得很多（一关 15 步的模拟 vs. 几行手工局面），谁空了谁领下一个，比事先平均分组更均衡；
- **输出顺序与调度无关**：主线程按下标顺序 `takeTMVar`，哪个工人先算完都一样；
- **必须完全求值**：`evaluate` 只到 WHNF，所以传入 `forceLines`（每一行的每个字符都 `seq`）——否则工人只算出第一个 `(:)`，
  真正的计算又回到主线程，并行就白做了；
- **异常按顺序报**：任务里的 `error` 存进槽里，主线程取到那一格时重抛，所以多个任务出错时报的是**按顺序第一个**，与串行求值相同。

## 4. 类型能挡住什么，挡不住什么（附实测数据）

| 错误 | 改动前 | 改动后 |
|------|--------|--------|
| 可变数组泄漏出去、被别处改掉 | 不用可变状态，不存在 | `runSTArray :: (forall s. ST s (STArray s i e)) -> Array i e`：`s` 由 `runSTArray` 选，带 `s` 的数组不可能出现在结果里，编译不过 |
| 在纯代码里偷偷做 IO（计时、打日志） | — | `ST s` 不是 `IO`，没有 `liftIO`；`applyGravityWith` 的类型仍是 `Registry -> MBoard -> MBoard` |
| 往 unboxed 数组里放 thunk / 任意类型 | — | `UArray` 只接受有 `IArray UArray e` 实例的原始类型，`UArray Pos (Maybe Color)` 编译不过 |
| 两个工人领到同一个任务 / 漏领 | — | 「读下标、加一」在同一个 `atomically` 里；STM 事务不能做 IO（`STM` 不是 `IO`），重跑是安全的 |
| 结果槽写两次 | — | `TMVar` 满时 `putTMVar` 阻塞；每个下标只被领一次，所以只写一次 |

**类型挡不住的：**

- **码的编码是否忠实**（`-1` 和颜色编号会不会撞、`toEnum` 能不能还原）——靠 `perf_match_scan_same_as_legacy` 逐格对照；
- **双指针的边界**（写指针越过读指针、空洞区间差一）——`ST` 只保证可变性不外泄，不保证算法对；靠两份重力对照测试；
- **并行时是否真的在工人线程里算完**——类型上 `evaluate x` 和 `evaluate (force x)` 都是 `IO ()`，只有计时能看出区别；
- **顺序**——`parallelForce` 返回 `[a]`，按什么顺序是实现决定的，测试用 1000 个工人去打乱调度。

**实测数据**（本机 8 核，GHC 9.14.1，`-O1`；box 是共享机器，墙钟有 ±0.5 s 左右的噪声，下面取多次运行的中位数）。

整体：三版库分别构建——A = 第 5 项前（`d44c242`）、B = 只改匹配码 / 提示、C = 最终（再加 ST 重力）——各跑金标准 / 元素查询生成器（单线程，与 `regen.sh` 相同）：

| 生成器 | A 基线 | B 匹配码 | C 最终 | A → C |
|-------|------:|------:|------:|------:|
| 金标准 `Golden`（3373 行） | 8.61 s | 6.85 s | 6.29 s ~ 6.55 s | −24 % ~ −27 % |
| 元素查询 `ElementQueries`（1666 行） | 2.38 s | 2.12 s | 1.99 s | −16 % |
| 金标准的堆分配（`+RTS -s`） | 29.6 GB | — | 19.2 GB | −35 % |
| 金标准的 GC 时间 / 最大驻留 | 0.48 s / 2.35 MB | — | 0.41 s / 2.32 MB | 基本不变 |

B → C（重力）另交替各跑 5 次：B 6.44 / 6.53 / 6.88 / 7.38 / 8.40 s，C 6.35 / 6.44 / 6.55 / 6.89 / 7.99 s——
差别（约 0.1–0.3 s）和噪声同一量级，与剖析里重力只占 2.4 % 一致。**整体收益几乎全部来自匹配码。**

测试套件（`stack test` 的同一个测试程序，`-threaded -N`，tasty 默认按核数并行跑各用例）：

| 项 | A 基线（412 个测试） | C 最终（417 个） |
|----|------:|------:|

## 5. 取舍

- **行为不变**。验证：金标准 3373 行、元素查询快照 1666 行重新生成后与入库文件 `cmp` 逐字节相同；原有 412 个测试全过，新增 5 个（共 417 个）；
  `make check`（网页版 state / anim 一致性 + e2e）通过。
- **ST 版提示搜索没有采用**。先写的是 ST 版：把码 `thaw` 进 `STUArray`，每个候选「就地换过去、查被触及的行 / 列、换回来」。
  量下来和「读码时对调两个下标」的纯函数写法一样快（7.48 vs 7.32 µs）——收益来自 unboxed 码数组和不复制盘面，**不是来自可变**。
  纯函数版更短、没有「忘了换回来」这种错误的可能，所以留纯函数版；ST 版保留在 `demo/MatchBench.hs` 作对照。
- **重力的 ST 版收益很小，仍然保留**。微基准 2.5×，但重力只占总时间 2.4 %，整体差别在噪声里（§4）。保留它是因为：
  它就是本项要展示的「纯接口背后的局部可变」，代码不比列表版长，而且有两份对照测试兜着；如果只看收益，这一处不改也可以。
  列表版 `colGravityWith` 仍在（`Board.Gravity` 的其他函数和测试在用）。
- **unboxed 码数组的代价**：每次扫描都先建一张整盘数组（81 个 `Int`）。只看一行一列的场景（比如只问某一格）会比旧写法多做事；
  本仓库的调用方都是整盘扫描，所以没有这个问题。码只编码「匹配颜色」，**新增影响匹配的属性**（比如某种元素只与同类连）就要改编码——
  注释和 `perf_match_scan_same_as_legacy` 的逐格对照会在第一时间暴露。
- **并行只在测试里**。游戏逻辑是纯的单线程状态机，网页版是单线程 wasm；`Golden.main`（重新生成快照）也保持串行，
  这样生成器不需要 `-threaded`、`regen.sh` 不变。测试组件新增依赖 `stm`（GHC 自带）；库和网页版没有新依赖。
- **没用 `async` / `parallel` 包**。`Control.Concurrent.Async.mapConcurrently` 或 `Control.Parallel.Strategies.parListChunk` 都能做同样的事，
  而且更短；这里手写 `forkIO` + STM 是为了不加依赖，也为了把「动态领任务、按顺序取回、异常按顺序重抛」写清楚。
- **下一个热点是注册表按名字查找**（`bodyOf` / `caps` / `levelNameOf` / `eqString`），见 §2；这一项不动。
- **网页版**：`Board.Match` / `Board.Gravity` 都在 wasm 里（Haskell2010 + `-Wall -Werror`，`ScopedTypeVariables` 按模块打开，
  `array` 原来就在网页版依赖里）；wasm 产物单独一个提交。

## 6. 复习小抄

| 想要 | 写法 | 本仓库的例子 |
|------|------|-------------|
| 先找热点 | `stack build --profile`，`-fprof-auto-top` 编译驱动程序，`+RTS -p` 看 `.prof` | §2 的剖析表 |
| 紧凑、严格、快读的数组 | `UArray i Int` / `UArray i Bool`（`Data.Array.Unboxed`） | `matchCodesWith` |
| 按需求值、最多算一次的表 | boxed `Array`（元素惰性） | `findHintWith` 的 `rowHas` / `colHas` |
| 纯接口背后的局部可变 | `runSTArray $ do m <- newListArray …; …; pure m`（或 `runST` + `STRef`） | `applyGravityWith` |
| Haskell2010 里写 ST 局部函数 | 写签名 `forall s. STArray s … -> ST s ()`，打开 `ScopedTypeVariables` | `compactSegment` |
| 「交换后」的视图而不复制 | 读的时候对调两个下标：`at q | q == p1 = arr ! p2 …` | `swapMakesMatch` |
| 多线程领任务 | `atomically (readTVar next >>= \i -> writeTVar next (i + 1) …)` | `parallelForce` 的 `claim` |
| 等结果、按顺序收 | 每任务一个 `TMVar`，主线程依次 `takeTMVar` | `parallelForce` |
| 在工人线程里真的算完 | `evaluate (force x)`，`force` 要到底（不是 WHNF） | `forceLines` |
| 量速度 | `getCPUTime`（微基准）/ `time`（墙钟）/ `+RTS -s`（分配、GC） | `demo/MatchBench.hs`、`demo/ParGolden.hs` |
| 记住 | 先量再改；可变 ≠ 更快（ST 版提示搜索）；局部 2.5× ≠ 整体 2.5×（重力）；用例并行 ≠ 套件并行（tasty） | §4、§5 |
